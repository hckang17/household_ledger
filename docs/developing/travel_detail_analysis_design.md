# 여행 상세·여행 분석 화면 설계안

> 작성일: 2026-09-08  
> 상태: 핵심 상세·분석 구현 완료 — 여행 CSV 백업 및 사용자 숙박비 태그 통합 안내는 후속  
> 관련 문서: `docs/developing/travel_mode_design.md`

## 구현 현황 (2026-09-08)

- 여행별 총액 그룹 조회, 여행 요약 계산기와 Provider 구현
- 여행 관리 카드의 총 지출·예산 진행률 및 여행 상세 진입 구현
- 여행 상세의 예산·핵심 지표, 여행 전·중·후/날짜별 지출 목록과 편집 구현
- 분석 화면의 `기간별 분석 / 여행별 분석` 전환과 여행 전용 분석 Widget 구현
- 시스템 숙박비 카테고리 `A`와 한·일 현지화 추가
- 기존 사용자 숙박비 태그는 자동 삭제하거나 재분류하지 않고 보존

후속 범위는 여행 메타데이터와 `tripId`의 CSV 전체 왕복, 기존 사용자 숙박비 태그를 시스템 `A`로 합칠지 묻는 일회성 안내다.

## 1. 목적

현재 구현된 여행 CRUD, 여행 모드, 지출의 `tripId` 연결을 바탕으로 다음 기능의 정보 구조와 구현 경계를 정한다.

1. 여행 관리 화면에서 여행을 선택하면 해당 여행의 요약과 지출 내역을 조회한다.
2. 기존 분석 화면에 월별·기간별 분석과 구분되는 여행별 분석을 제공한다.
3. 예산, 여행 일수, 일평균 여행비, 교통비, 숙박비, 카테고리별 지출을 일관된 기준으로 계산한다.
4. 여행 전후에 결제한 항공권·숙박비도 여행 총비용에는 포함하면서, 실제 여행 기간 중 지출과 구분해 보여준다.
5. 현재 기본 소비 카테고리에 없는 `숙박비`를 데이터 호환성을 고려해 추가한다.

이 문서는 화면 아이디어만이 아니라 집계 정의와 상태 흐름까지 포함한다. 지표의 의미를 먼저 고정하지 않으면 여행 상세 화면과 분석 화면에서 서로 다른 금액을 보여줄 수 있기 때문이다.

## 2. 핵심 결론

### 2.1 여행 상세가 기본 진입점이다

여행 관리 화면의 각 카드를 누르면 `TravelDetailPage`로 이동한다. 이 화면에서 해당 여행의 핵심 요약과 모든 연결 지출을 함께 보여준다.

- 여행 관리 화면: 여러 여행을 찾고 상태를 관리하는 목록
- 여행 상세 화면: 한 여행의 현황과 지출 기록을 확인하는 기본 화면
- 여행별 분석 화면: 한 여행의 소비 패턴을 더 자세히 살펴보는 분석 화면

대부분의 사용자는 여행 카드를 선택한 뒤 바로 총비용과 지출 목록을 보고 싶어 한다. 따라서 단순 조회를 위해 분석 탭까지 이동하게 만들지 않는다.

### 2.2 여행 분석을 기존 기간 모드에 섞지 않는다

기존 분석 화면의 월별·특정 기간 선택은 모두 **시간 범위로 전체 데이터를 자르는 방식**이다. 반면 여행 분석은 날짜가 아니라 `tripId`로 데이터를 선택한다.

또한 여행 분석에는 다음 기존 요소가 그대로 적용되지 않는다.

- 수입 분석
- 전월 동기 비교
- 고정지출 집계
- 전체 소비의 식생활 분석
- 월 이동 버튼

따라서 기존 `월별 / 기간 지정` 옆에 `여행`을 세 번째 기간 모드로 추가하지 않는다. 분석 화면 최상단에 다음과 같은 상위 범위를 둔다.

```text
┌─────────────────────────────────────┐
│ 분석                                │
│ [ 기간별 분석 ]  [ 여행별 분석 ]    │
└─────────────────────────────────────┘
```

- `기간별 분석`: 현재 분석 UI와 동작을 그대로 유지한다.
- `여행별 분석`: 여행 선택기와 여행 전용 분석 Widget을 표시한다.

이 구조는 현재 기능의 회귀 위험을 줄이고, 향후 여행끼리 비교하는 기능도 독립적으로 확장할 수 있다.

### 2.3 계산 로직은 공유하고 화면 Widget은 목적별로 분리한다

기존 분석 Widget을 여행 화면에 억지로 재사용하지 않는다. 여행 상세와 여행 분석은 밀도와 사용 목적이 다르므로 별도 Widget으로 만든다.

공유할 대상:

- `TravelSummaryCalculator`
- `TravelSummary`와 세부 결과 모델
- 통화 포맷 Extension
- 작은 공통 UI primitive가 실제로 동일한 경우

분리할 대상:

- 여행 상세의 간결한 요약 카드
- 여행 분석의 상세 카테고리 차트
- 여행 지출의 시점별·일별 분석
- 여행 상세의 지출 목록과 편집 동작

즉, **데이터와 계산 결과는 공유하되 화면 구성은 공유를 강제하지 않는다.**

## 3. 여행 지출의 집계 기준

### 3.1 연결 기준

여행별 데이터의 기준은 날짜가 아니라 명시적으로 저장된 `tripId`다.

```text
여행 전체 지출
  = ExpenseEntry.tripId == 선택한 여행 ID

여행 기간 중 지출
  = tripId 일치
  AND trip.startDate <= spentAt 날짜 <= trip.endDate

여행 전 지출
  = tripId 일치 AND spentAt 날짜 < trip.startDate

여행 후 지출
  = tripId 일치 AND spentAt 날짜 > trip.endDate
```

항공권이나 숙박 예약비처럼 여행 전에 결제한 비용도 `여행 전체 지출`과 예산 사용액에는 포함한다. 여행 기간은 지출 연결의 제약이 아니라 지출 시점을 설명하는 보조 데이터다.

### 3.2 핵심 지표 정의

| 지표 | 계산 | 예외 처리 |
|---|---|---|
| 총 여행비 | 연결된 모든 지출 합계 | 0건이면 0 |
| 여행 일수 | `endDate - startDate + 1일` | 최소 1일로 방어 |
| 1일당 여행비 | 총 여행비 ÷ 계획된 여행 일수 | 정수 통화 표시 규칙에 맞게 반올림 |
| 여행 기간 중 지출 | 기간 안의 연결 지출 합계 | 시작일·종료일 포함 |
| 여행 전후 지출 | 기간 밖의 연결 지출 합계 | 전/후 금액을 별도로도 제공 |
| 사용 예산 | 총 여행비 | 사전 결제도 예산에 포함 |
| 남은 예산 | 예산 - 총 여행비 | 음수면 초과 금액으로 표시 |
| 예산 사용률 | 총 여행비 ÷ 예산 × 100 | 예산이 없거나 0이면 `null` |
| 교통비 | `categoryCode == 'T'`인 연결 지출 합계 | 0건이면 0 |
| 숙박비 | 신규 숙박 시스템 카테고리의 연결 지출 합계 | 카테고리 정책은 7장 참고 |
| 카테고리별 지출 | 연결 지출을 `categoryCode`로 합산 | 금액 내림차순 |
| 결제수단별 지출 | 연결 지출을 `paymentMethodCode`로 합산 | 상세 분석의 보조 항목 |

`1일당 여행비`는 결제일이 아닌 여행의 계획 일수로 나눈다. 예를 들어 3일 여행의 호텔비를 한 달 전에 결제했어도 3일 여행에 필요한 비용이므로 일평균 여행비에 포함한다. 화면 설명에는 `사전·사후 결제 포함`을 명시한다.

### 3.3 일별 차트 기준

연결된 지출 전체를 결제일 순서로 하나의 차트에 그리면 몇 달 전의 항공권 때문에 실제 여행 3일 구간이 지나치게 압축될 수 있다. 기본 일별 차트에는 **여행 기간 안의 지출만** 표시한다.

- X축: 여행 1일차, 2일차, 3일차 …
- Y축: 해당 날짜의 지출 합계
- 지출이 없는 날도 0으로 표시
- 여행 전·후 지출은 차트 밖의 별도 요약 카드로 표시

향후 필요하면 `결제일 기준 전체 흐름`을 보조 차트로 추가하되 MVP에는 포함하지 않는다.

## 4. 여행 관리 화면 개편

현재 여행 카드는 이름, 기간, 예산과 수정·보관 버튼을 보여준다. 여기에 총 지출과 예산 상태를 추가하고, 카드 본문을 상세 화면 진입 영역으로 만든다.

```text
┌─────────────────────────────────────┐
│ ✈ 제주 가족여행        [사용 중]    │
│ 2026.09.03 - 2026.09.05 · 완료      │
│                                     │
│ 총 지출  523,000원                  │
│ 예산      700,000원 · 75% 사용      │
│ ━━━━━━━━━━━━━━━────────             │
│                                     │
│ [수정] [보관]                  [>]   │
└─────────────────────────────────────┘
```

권장 상호작용:

- 카드 본문 또는 우측 화살표: 여행 상세 열기
- `수정`: 여행 정보 편집 Sheet 열기
- `보관/복원`: 현재 동작 유지
- 활성 여행 Chip: 현재 여행 모드 상태 표시
- 긴 여행명: 한 줄 말줄임, 접근성 레이블에는 전체 이름 제공

목록에서 여행별 합계를 보여주려면 여행마다 DB를 순차 조회하지 않는다. 한 번의 집계 쿼리 또는 모든 여행 ID의 합계를 묶어 반환하는 Provider를 사용해 N+1 조회를 피한다.

## 5. 여행 상세 화면

### 5.1 화면 구조

```text
┌─────────────────────────────────────┐
│ ← 제주 가족여행                 ⋮   │
├─────────────────────────────────────┤
│ 2026.09.03 - 09.05 · 3일            │
│ 완료 · 메모                         │
├─────────────────────────────────────┤
│ 총 여행비             523,000원     │
│ 예산                  700,000원     │
│ 남은 예산             177,000원     │
│ ━━━━━━━━━━━━━━━──────── 74.7%       │
├─────────────────────────────────────┤
│ 1일당 여행비 │ 교통비 │ 숙박비      │
│ 174,333원     │ 80,000 │ 210,000     │
├─────────────────────────────────────┤
│ 결제 시점                            │
│ 여행 전 250,000 │ 여행 중 263,000   │
│ 여행 후  10,000                     │
├─────────────────────────────────────┤
│ 지출 내역                    [추가]  │
│ 여행 전                              │
│ 08.10 항공권              180,000원 │
│ 08.15 호텔 예약금           70,000원 │
│ 여행 중                              │
│ 09.03 공항철도              12,000원 │
│ ...                                  │
├─────────────────────────────────────┤
│            [자세히 분석]             │
└─────────────────────────────────────┘
```

### 5.2 지출 목록

지출은 다음 섹션으로 나눠 표시한다.

1. 여행 전
2. 여행 기간 중 — 날짜별 그룹
3. 여행 후

각 행은 날짜, 내용, 카테고리, 금액을 보여주고 누르면 기존 지출 수정 Sheet를 연다. 수정 후 해당 여행 지출 Provider와 여행 요약 Provider를 함께 invalidate한다.

`추가` 버튼은 선택한 여행을 명시적으로 초기값으로 전달한다. 현재 다른 여행 모드가 켜져 있어도 상세 화면에서 추가한 지출은 보고 있던 여행에 연결해야 한다. 이를 위해 향후 `showExpenseEditorSheet`에 `initialTripId` 같은 명시적 인자를 추가하고, 명시적 인자가 활성 여행보다 우선하도록 한다.

### 5.3 상세 화면 액션

AppBar의 더보기 메뉴에 다음을 둔다.

- 여행정보 수정
- 여행 모드로 사용
- 보관 또는 복원
- 지출 연결 관리

영구 삭제는 연결 지출 처리 정책이 정해질 때까지 제공하지 않는다. 보관은 데이터와 집계를 유지한다.

## 6. 분석 화면의 여행별 분석

### 6.1 상위 분석 범위

분석 화면의 최상단에 `기간별 분석 / 여행별 분석` SegmentedButton을 추가한다.

```text
기간별 분석
  └─ 현재 월별/기간 지정 컨트롤
  └─ 지출/수입 탭
  └─ 전월 동기, 고정지출, 음식 분석

여행별 분석
  └─ 여행 선택 컨트롤
  └─ 여행 지출 전용 요약과 차트
```

여행별 분석에서는 지출/수입 탭을 숨긴다. 여행에 수입을 연결하는 모델이 없기 때문이다. 전월 동기 비교도 숨기고, 향후 별도 기능으로 `다른 여행과 비교`를 검토한다.

### 6.2 여행 선택기

```text
┌─────────────────────────────────────┐
│ 분석할 여행                         │
│ [ 제주 가족여행 · 09.03~09.05  ▼ ] │
│ [전체] [예정] [완료] [보관됨]       │
└─────────────────────────────────────┘
```

- 기본 선택 우선순위: 활성 여행 → 가장 최근 여행 → 없음
- 보관된 여행도 과거 분석을 위해 선택 가능
- 여행 이름이 중복되므로 기간을 항상 함께 표시
- 여행이 없으면 새 여행 생성 CTA 표시
- 선택한 여행 ID만 화면 상태로 유지하고 여행 객체는 Provider에서 다시 조회

### 6.3 여행 분석 전용 구성

권장 표시 순서:

1. 예산 요약과 진행률
2. 총 여행비, 1일당 여행비, 지출 건수
3. 교통비와 숙박비 강조 카드
4. 카테고리별 지출 막대 또는 도넛 차트
5. 여행 기간의 일자별 지출 차트
6. 여행 전·중·후 지출 비율
7. 결제수단별 지출 — 접힌 보조 섹션

카테고리별 분석은 도넛만 사용하기보다 금액과 비율을 동시에 읽기 쉬운 가로 막대 목록을 우선 검토한다. 카테고리가 많을 때 작은 도넛 조각보다 비교가 쉽고 작은 화면에도 안정적이다.

교통비와 숙박비는 대표 지표로 상단에 강조하지만, 아래 카테고리별 합계에도 포함한다. 같은 금액을 두 곳에 표시하는 것은 중복 집계가 아니라 빠른 확인과 상세 분석이라는 서로 다른 목적이다.

### 6.4 여행 상세와 분석 화면의 관계

여행 상세의 `자세히 분석` 버튼은 분석 탭의 여행별 분석을 선택한 상태로 이동하고 해당 `tripId`를 초기 선택값으로 전달한다.

반대로 분석 화면에서 여행명을 누르면 여행 상세 화면으로 이동할 수 있다. 두 화면이 서로의 전체 Widget 트리를 공유할 필요는 없지만 같은 `TravelSummary` 결과를 사용해 금액 불일치를 막는다.

## 7. 숙박비 카테고리 정책

### 7.1 숙박비는 대분류가 적절하다

현재 소비 소구분은 `평상시(_) / 여행(t)`라는 사용 맥락을 표현한다. `숙박비`는 여행 여부와 별개인 소비 목적이므로 소구분이 아니라 대분류에 추가하는 것이 맞다.

권장 시스템 카테고리:

```text
code: A
ko: 숙박비
jp: 宿泊費
```

예시:

```text
호텔 예약
  categoryCode: A       // 숙박비
  subcategoryCode: t    // 여행
  tripId: trip-123
```

숙박비는 여행 외에도 출장, 임시 거주 등에서 사용할 수 있으므로 특정 여행에 종속된 전용 필드로 만들지 않는다.

### 7.2 기존 데이터 호환

새 시스템 태그를 추가할 때 다음을 함께 처리한다.

- `systemMetadataTagLocalizationKeys`에 `A` 추가
- 한·일 시스템 태그 문구 추가
- 양 언어의 예약된 태그 이름에 `숙박비`, `宿泊費` 추가
- 신규·기존 설치 모두 누락된 시스템 태그를 보완
- 기존 JSON과 CSV에 `A`가 없어도 정상 복원
- 사용자가 이미 같은 이름의 사용자 카테고리를 만든 경우 중복 처리

같은 이름의 사용자 카테고리가 이미 존재할 수 있으므로 조용히 삭제하거나 코드를 재해석하지 않는다. 권장 방식은 한 번만 표시되는 통합 안내다.

```text
기본 '숙박비' 카테고리가 추가되었습니다.
기존에 만든 '숙박비' 카테고리의 기록을 기본 카테고리로 통합할까요?

[나중에] [통합]
```

`통합`은 기존 태그 삭제 로직과 같은 순서를 따른다.

1. 기존 사용자 숙박 태그에 연결된 지출과 고정지출을 `A`로 변경
2. 저장소 변경 성공 확인
3. 메모리 상태 갱신
4. 기존 사용자 태그 제거

이 migration은 반복 실행해도 결과가 같아야 한다. 자동 통합 구현이 부담된다면 첫 단계에서는 기본 숙박비를 추가하되 충돌 사용자는 기존 사용자 태그를 보존하고, 여행 분석의 숙박비 강조 카드는 시스템 `A`만 집계한다는 제한을 명시한다.

### 7.3 자동 재분류는 하지 않는다

기존 `기타`, `생활비` 등에 입력된 호텔 지출을 설명 문자열로 추측해 숙박비로 옮기지 않는다. 사용자가 여행 상세의 지출 목록이나 데이터 관리 화면에서 직접 변경하게 한다.

### 8.2 결과 모델 예시

```dart
class TravelSummary {
  final int totalExpense;
  final int expenseCount;
  final int tripDayCount;
  final int averagePerTripDay;
  final int beforeTripExpense;
  final int duringTripExpense;
  final int afterTripExpense;
  final int transportExpense;
  final int accommodationExpense;
  final int? budget;
  final int? remainingBudget;
  final double? budgetUsagePercent;
  final List<TravelBreakdownItem> categoryBreakdown;
  final List<TravelBreakdownItem> paymentMethodBreakdown;
  final List<TravelDailyAmount> dailyAmounts;

```

결과 모델에는 번역된 라벨, 색상, `BuildContext`를 넣지 않는다. 코드에서 화면 라벨로 바꾸는 작업은 View가 현재 언어팩과 메타데이터 태그를 이용해 처리한다.

### 8.3 Provider 흐름

```text
travelExpensesProvider(tripId)
  -> ExpenseDatabaseService.loadExpensesByTrip(tripId)

travelSummaryProvider(tripId)
  -> travelProvider에서 Trip 조회
  -> travelExpensesProvider에서 연결 지출 조회
  -> TravelSummaryCalculator 계산
  -> 불변 TravelSummary 반환
```

지출 추가·수정·삭제 후에는 다음 범위를 함께 갱신한다.

- `monthlyExpensesProvider`
- `rangeExpensesProvider`
- 변경 전 `tripId`의 `travelExpensesProvider`
- 변경 후 `tripId`의 `travelExpensesProvider`
- 여행 목록 합계 Provider

지출을 A여행에서 B여행으로 옮기는 수정에서는 A와 B를 모두 invalidate해야 한다.

### 8.4 성능 원칙

- 상세 화면은 이미 존재하는 `loadExpensesByTrip`과 `tripId` 인덱스를 사용한다.
- 한 여행의 원본 지출을 한 번 조회한 뒤 모든 요약을 메모리에서 한 번에 계산한다.
- 각 카드가 별도 Provider로 같은 DB를 반복 조회하지 않는다.
- 계산 복잡도는 지출 수에 대해 O(n)을 유지한다.
- 여행 목록 합계는 여행 수만큼 개별 쿼리하지 않고 그룹 집계 API를 추가한다.
- 차트 애니메이션은 화면 진입 시에만 짧게 재생하고 스크롤 때마다 재시작하지 않는다.

## 9. 빈 상태와 특수 사례

| 상황 | 권장 처리 |
|---|---|
| 여행이 한 건도 없음 | 여행별 분석 대신 `새 여행 만들기` CTA |
| 여행은 있으나 연결 지출 0건 | 0원 카드보다 설명형 빈 상태와 `지출 추가` 제공 |
| 예산 미설정 | 잔액·사용률을 숨기고 `예산 설정` 링크 표시 |
| 예산 초과 | 남은 예산 대신 `초과 00원`, 진행률 색상을 경고색으로 표시 |
| 여행 기간 밖 지출 | 총 여행비에는 포함하고 전/후 섹션으로 분리 |
| 당일치기 여행 | 여행 일수 1일, 1일당 여행비는 총 여행비와 동일 |
| 시작일과 종료일의 시각 차이 | 날짜 단위로 정규화하고 양 끝 날짜 포함 |
| 예정 여행의 사전 결제만 존재 | 총 여행비와 예산 사용률 표시, 여행 중 차트는 0 |
| 보관된 여행 | 상세·분석 조회 허용, 신규 지출 기본 선택에서는 제외 |
| 중복 여행명 | 선택기와 제목에 기간을 함께 표시 |
| 연결된 여행이 없는 `tripId` | 정상 데이터로 숨기지 말고 데이터 무결성 오류 상태 표시 |
| 여행 소구분이지만 `tripId == null` | `미분류 여행 지출` 관리 진입점 제공, 특정 여행 합계에는 미포함 |
| 고정지출 | 현재 `tripId`가 없으므로 여행 합계에서 제외 |
| 수입 | 여행 연결 모델이 없으므로 여행 분석에서 제외 |
| 통화 변경 | 저장 금액은 정수 유지, 현재 앱 통화 포맷으로 표시 |

## 10. 단계별 구현 권장 순서

### Phase 1 — 계산 계약

- `TravelSummary`, 시점 구분, 일별 결과 모델 작성
- `TravelSummaryCalculator` 작성
- 기간 전·중·후, 양 끝 날짜, 0건, 예산 없음·초과, 당일치기 테스트

### Phase 2 — 조회 Provider와 무효화

- `travelExpensesProvider(tripId)` 추가
- `travelSummaryProvider(tripId)` 추가
- 지출 CRUD 후 이전·새 여행 Provider invalidate
- 여행 목록용 그룹 합계 조회 추가

### Phase 3 — 여행 상세 화면

- 고정 상세 route와 타입 안전한 `tripId` 인자 처리
- 여행 카드 탭 동작
- 예산·핵심 지표·시점별 요약
- 전·중·후 지출 목록과 편집
- 상세 화면에서 해당 여행으로 지출 추가

### Phase 4 — 여행별 분석

- 분석 화면에 상위 범위 선택 추가
- 여행 선택기와 빈 상태
- 여행 전용 카테고리·일별·시점별 Widget 작성
- 여행 상세에서 선택된 여행 분석으로 이동

### Phase 5 — 숙박비 카테고리

- 시스템 카테고리 `A` 추가
- 사용자 태그 이름 충돌 정책 구현
- 기존 데이터, 태그 삭제·대체 순서, 한·일 현지화 테스트

### Phase 6 — 백업 완성

현재 여행 메타데이터의 CSV 백업은 아직 후속 범위다. 상세·분석 기능을 사용자에게 정식 제공하기 전 `[TRIPS]`와 `tripId`의 전체 round-trip을 완성하는 것이 안전하다. 분석 결과 자체는 백업하지 않고 원본 여행과 지출에서 다시 계산한다.

## 11. 완료 기준

- 여행 카드를 누르면 같은 여행의 상세 화면이 열린다.
- 상세 총액과 분석 총액이 같은 `TravelSummary`를 사용해 항상 일치한다.
- 여행 전·후 결제도 총액과 예산에 포함된다.
- 여행 기간 일별 차트에는 기간 안의 지출만 표시된다.
- 여행 시작일과 종료일은 기간 중 지출로 집계된다.
- 상세 화면에서 추가한 지출은 다른 활성 여행이 있어도 현재 여행에 연결된다.
- 지출을 다른 여행으로 옮기거나 연결 해제하면 양쪽 화면이 즉시 갱신된다.
- 예산 없음, 예산 초과, 지출 0건, 당일치기, 보관 여행이 안전하게 표시된다.
- 기존 기간별 분석 UI와 결과가 바뀌지 않는다.
- 숙박비 시스템 태그 추가가 기존 사용자 태그나 지출을 조용히 삭제하지 않는다.
- 한국어와 일본어의 모든 새 문구와 placeholder가 일치한다.

## 12. MVP에서 제외할 항목

다음 기능은 현재 모델에 억지로 포함하지 않는다.

- 여행 간 비용 비교와 순위
- 여행 수입 또는 환급금
- 동행자별 정산
- 다중 통화와 환율
- 국가·도시별 분석
- 영수증 이미지
- 여행별 고정지출
- 자동 카테고리 추론

첫 구현은 `한 여행에 연결된 지출을 정확히 조회하고, 예산과 핵심 비용 구조를 이해하기 쉽게 보여주는 것`에 집중한다.
