# Android 베타테스트 보고서

> **검사 기간: 2026-09-11~15. Android 에뮬레이터 베타테스트 결과 보고서.** 확인된 문제 16건과 재현 절차·증거·개선 방향을 기록했다. 실물 기기 및 장기간 검증이 필요한 항목은 별도로 명시했다.

## 검사 대상과 방법

- 앱: Household Ledger 1.0.0+1, Flutter 3.44.0 / Dart 3.12.0.
- 기준: `cd5c137`(2026-09-14 재개 시점). 9월 11일의 1차 자동 검사 기준은 `ec88913`이었다. 재개 후 현재 소스로 Android x86_64 debug APK를 다시 빌드했다.
- Android 16 / API 36 Google APIs x86_64 전용 에뮬레이터에 신규 설치했다. 개인 휴대전화의 가계부 데이터는 사용하지 않았다.
- 실제 Android 터치 입력, 시스템 파일 선택/공유, 화면 캡처, SQLite 저장 결과를 검사한다. 서로 다른 물리 기기 여러 대를 사용한 시험은 아니다. 한 에뮬레이터의 해상도·밀도·글자 크기를 바꿨다.
- 별도로 실제 페이지 16개 × 6조건을 Flutter Widget 환경에서 렌더링했다. 이 검사는 Windows 호스트 글꼴과 가짜 플러그인 경로를 사용하므로 **Android 재현과 별도**로 해석한다. 처음 사용한 Ahem 테스트 글꼴의 결과는 결함 판정에서 제외하고 읽을 수 있는 글꼴로 다시 실행했다.
- 앱 코드는 수정하지 않았다. 이 폴더의 검사 스크립트·캡처·결과만 작성했다.

### B01. 작은 화면에서 소비기록을 정상적으로 볼 수 없음

1. 640×1136px, density 320(320×568dp), 기본 글자 크기로 실행한다.
2. 하단 `소비기록`을 연다. 2026년 9월 달력이 펼쳐진 상태다.
3. 달력 하단과 그 아래 영역이 화면을 벗어나며 기록 버튼과 겹친다. Android debug 화면에는 `BOTTOM OVERFLOWED BY 256 PIXELS`가 표시된다(Flutter 논리 픽셀 기준).

360×640dp, 시스템 글자 1.8 설정에서는 `348 PIXELS` 넘침과 요일 줄바꿈도 확인했다. 폰트만 작게 고정해서 해결하면 접근성이 나빠진다. 달력과 내역을 하나의 스크롤 구조로 구성하거나, 가용 높이에 따라 달력을 접고 날짜 선택 기능을 유지하는 방향이 필요하다.

근거: [작은 Android 화면](beta_test_evidence/android_matrix_small_expense.png), [큰 글자 화면](beta_test_evidence/android_matrix_largefont_expense.png), `lib/presenter/pages/expense_page/expense_record_page.dart`의 본문 `Column`, `expense_calendar_section.dart`의 고정 높이 달력 셀.

### B02. 불완전한 백업을 정상 복원 대상으로 인정

정상 내보내기로 만든 v3 파일을 `[TAGS]` 섹션 표시 직후에서 잘라 파서에 전달했다. 결과는 `success: true`였고, 태그는 22개에서 식사 유형 7개만 남았다. `[EXPENSES]` 섹션의 헤더와 데이터만 제거한 파일도 지출 0건인 정상 파일로 처리됐다.

가져오기가 기존 DB 전체를 교체하므로 잘못된 파일이 사용자 데이터 손실로 이어질 수 있다. 섹션 존재뿐 아니라 필수 헤더·레코드 완결성을 검사하고, 백업 전체의 건수/해시를 검증해야 한다. 복원 직전에는 데이터 종류별 건수를 보여주는 것이 좋다.

근거: [검사 결과](beta_test_evidence/backup_probe.json), [재현 코드](beta_test_evidence/backup_probe_test.dart). 이 검사는 파서의 수락 여부까지 확인했으며, 손상 파일로 실제 사용자 DB를 덮어쓰지 않았다.

### B03. 중복 수입 ID가 조용히 덮어써짐

수입 `id=1, 1,000`과 `id=2, 2,000`인 정상 백업에서 두 번째 ID를 1로 바꿨다. 파서는 수입 2건을 정상 반환했지만, 실제 SQLite `upsertIncomes` 저장 후에는 1건/2,000만 남았다. 기대 합계는 3,000이다.

지출·여행·고정지출과 동일하게 수입 ID의 중복도 파싱 단계에서 거부해야 한다. 실제 저장 뒤 건수·합계를 검증하면 추가 방어가 된다.

근거: [검사 결과](beta_test_evidence/backup_probe.json)의 `duplicate_income_id`; `data_im_export_service.dart`의 중복 검사에 수입이 빠져 있고 `income_database_service.dart`는 충돌 시 `replace`한다.

### B04. 분석 기간 탐색부의 가로 넘침

320×568dp, 일본어, 시스템 글자 1.3에서 `분석` → 기간별 분석을 연다. 날짜 `09.01 - 09.30`의 끝과 다음 달 화살표가 카드 오른쪽으로 밀려나고, `RIGHT OVERFLOWED BY 34 PIXELS`가 표시된다. 날짜/화살표를 포함하는 `Row`가 고정 크기 자식을 그대로 배치하는 것이 원인이다. 폭이 부족하면 기간 선택을 다음 줄로 분리하고 날짜 영역이 남은 폭 안에 들어오도록 해야 한다.

근거: [실제 Android](beta_test_evidence/android_japanese_analysis.png), `lib/presenter/widgets/analysis_page/analysis_period_control_card.dart`의 `_buildMonthNavRow`.

추가로 일본어 360×640dp, 글자 1.8에서도 **40 논리 픽셀** 넘침을 재현했다. 지출 0건 상태에서도 발생하므로 데이터 양 때문이 아니다. 상단 분석 유형 버튼도 단어 중간에서 여러 줄로 나뉜다. [추가 캡처](beta_test_evidence/android_final_largefont_japanese_analysis.png).

### B05–B06. 읽기와 접근성

- 기본 밝은 배경에서 상태바 시계·통신·배터리 아이콘이 흰색으로 표시된다. [홈 화면](beta_test_evidence/android_home_with_expense.png)처럼 대비가 매우 낮다. 배경 밝기에 맞는 시스템 상태바 아이콘 스타일이 필요하다.
- Android UI 계층에서 수입·고정지출의 이전/다음 달 버튼, 고정지출 목록의 수정/삭제, 메타데이터 추가/펼치기 버튼 일부는 이름 없는 `Button`으로 나온다. **TalkBack 음성으로 직접 청취한 결과는 아니며** UIAutomator 의미 정보와 소스의 `tooltip` 누락을 확인한 결과다. `이전 달`, `다음 달`, `Rent 수정`, `Rent 삭제`처럼 행동과 대상을 알 수 있는 이름을 붙이는 것이 좋다.
- 네이티브 증거: [수입 UI 계층](beta_test_evidence/android_income_saved.xml), [고정지출 UI 계층](beta_test_evidence/android_fixed_saved.xml), [태그 관리](beta_test_evidence/android_metadata_sections.xml).

### B07. 사용 가능한 것처럼 보이는 PDF 암호 입력

PDF 암호 필드에 테스트 문자열을 입력한 뒤 생성했으나 결과는 암호화되지 않은 PDF였다. 화면 하단에는 ‘현재 버전은 암호화 미지원’ 안내가 있으므로 **지원된다고 완전히 숨긴 것은 아니다.** 하지만 활성 입력란과 README의 ‘PDF 열람 시 입력 요구’ 설명은 서로 충돌한다.

현재 구현에서는 입력 컨트롤러만 있고 생성 요청으로 비밀번호를 전달하지 않는다. 구현 전에는 입력란을 숨기거나 비활성화하고, 한국어·일본어 README를 실제 동작에 맞춰야 한다. [실제 설정 화면](beta_test_evidence/android_pdf_form_options.png), [암호화 검사](beta_test_evidence/pdf_offline_verification.json).

### B08. 달력 현지화와 큰 글자

`Sun`–`Sat`가 코드에 고정되어 있다. 일본어로 바꿔도 영어가 유지되며, 글자를 확대하면 `Mon`, `Wed` 등이 두 줄로 갈라져 달력 높이를 더 차지한다. locale에 맞는 짧은 요일 표시와 충분한 셀 높이를 사용해야 한다. 언어 변경 직후의 저장 알림도 이전 한국어로 표시되는 모습을 확인했다. [일본어 달력](beta_test_evidence/android_japanese_expense.png), [언어 변경 직후 UI 계층](beta_test_evidence/android_profile_japanese_saved.xml).

### B09. 가로 화면에서 공통 팝업 입력·확인 불가

1. 환경설정에서 지출구분의 `+`를 눌러 태그 추가 창을 연다.
2. 입력란에 포커스를 둔 상태로 640×360dp 가로 화면을 적용한다.
3. 키보드 위 공간에 팝업을 맞추지 못해 186 논리 픽셀 넘침이 발생한다. 제목 일부만 남고 입력란과 저장·취소 버튼은 키보드 뒤로 내려간다.

`BootstrapDialog`의 전체 콘텐츠가 스크롤되지 않는 `Column`이다. 화면과 키보드로 줄어든 높이에 맞춰 본문을 스크롤하고 액션은 도달 가능한 위치에 두어야 한다. [정착된 가로 프레임](beta_test_evidence/android_tag_landscape_settled.png). XML에는 가려진 컨트롤의 좌표가 남으므로 XML만으로 사용 가능 판정을 하면 안 된다.

### B10. 오프라인 PDF의 일본어 글꼴 누락

새 설치에서 PDF를 한 번도 생성하지 않은 상태로 Wi-Fi와 모바일 데이터를 끈 뒤 일본어 PDF를 생성했다. 앱은 성공을 표시했지만 결과 5쪽의 일본어 제목·범례·표 머리글이 모두 네모 문자로 보였다. 영문 이름과 숫자는 유지되어 더 쉽게 정상 생성으로 오인할 수 있다.

폰트를 `PdfGoogleFonts`로 받아오다가 실패하면 Helvetica로 대체하는 구현이다. 한·일 글꼴을 앱에 포함하거나, 필요한 글꼴이 없을 때 생성 성공으로 처리하지 말아야 한다. 한국어도 같은 대체 경로를 사용하므로 영향 가능성이 있으나, 이번 네이티브 파일은 **일본어**로 재현했다.

근거: [완료 안내](beta_test_evidence/android_pdf_offline_result.png), [표지](beta_test_evidence/pdf_offline_page_1.png), [표·차트](beta_test_evidence/pdf_offline_page_2.png), [생성 원본](beta_test_evidence/native_report_offline.pdf). 텍스트 추출뿐 아니라 5쪽을 모두 이미지로 렌더링해 검토했다.

네트워크를 켜고 다시 생성한 파일은 NotoSansJP 글꼴이 포함됐으며, 5쪽 모두 일본어가 정상 표시됐다. [온라인 생성 원본](beta_test_evidence/native_report_network_enabled.pdf), [글꼴 검사](beta_test_evidence/pdf_network_verification.json). 따라서 첫 오프라인 생성의 글꼴 준비 경로를 우선 수정해야 한다.

### B11. PDF 도넛과 범례 비율의 불일치

고정지출 800,000, 숙박 40,000, 외식 12,000으로 생성한 PDF에서 도넛은 일반 지출 52,000을 기준으로 숙박 약 77%·외식 약 23%를 그리지만, 범례는 고정지출을 포함한 852,000을 분모로 5%·1%를 표시한다. 같은 차트 안에서 서로 다른 분모를 사용한다. 총합 숫자 자체의 오류는 아니다.

고정지출을 도넛에도 포함하거나 일반 지출만을 기준으로 범례를 계산하고, 차트의 범위를 명시해야 한다. [PDF 2쪽](beta_test_evidence/pdf_offline_page_2.png), `export_pdf_report_service.dart`의 `combinedExpense` 백분율과 `pieSlices` 구성 확인.

두 지출을 BetaCategory로 일괄 변경한 뒤 온라인에서 재생성해도 도넛은 단일 카테고리 100%인데 범례는 6%였다. [글자가 정상인 재현 화면](beta_test_evidence/pdf_network_page_2.png).

### B12. 백업 보관 동작의 혼동

CSV는 앱 전용 외부 저장소 `Android/data/.../files/HouseLedger`에 생성된다. 완료 창은 긴 내부 경로와 `파일 공유`, `저장`을 보여주지만 `저장`은 창만 닫는다. Android 공유창에는 테스트 환경에서 Quick Share·Drive·Gmail이 있었고, Downloads에 저장하는 항목은 보이지 않았다.

일반 사용자는 이 파일을 다시 선택하거나 다른 기기로 옮기는 데 어려움을 겪을 수 있다. 파일을 보관할 위치를 직접 고르는 동작을 제공하고, 창 닫기는 `완료`로 이름을 구분하는 것이 좋다. 테스트에서는 원본을 보존한 채 **ADB로 Downloads에 복사해 파일 선택기를 검사**했다. 이것을 앱이 제공하는 다운로드 저장 기능으로 계산하지 않았다. [완료 창](beta_test_evidence/android_export_success.png), [공유창](beta_test_evidence/android_csv_share_sheet.png).

### B13. 튜토리얼 정리의 재시작 내구성 부족

`MockDataService`는 임시 데이터를 DB에 쓰지만 삭제할 ID는 메모리 `_insertedIds`에만 보관한다. 같은 DB에 대해 새 서비스 인스턴스로 정리를 호출하자 `__tutorial_mock__` 기록이 남았다. [재현 결과](beta_test_evidence/tutorial_restart_probe.json), [재현 코드](beta_test_evidence/tutorial_restart_probe_test.dart).

이는 실제 Android 프로세스를 종료한 전체 튜토리얼 시험이 아니라 **서비스 메모리 유실을 SQLite와 함께 재현한 검사**다. 결과의 1건/5,000은 해당 호스트 검사에서 남은 실제 수치이며 Android에서 항상 그 건수가 된다는 의미는 아니다. 영속된 임시 레코드 식별자를 조회해 정리하는 방어와, 튜토리얼 도중 강제 종료 후 재진입 회귀 시험이 필요하다.

### B14–B15. 편의성과 디자인 통일

- 검색은 완료되어도 `_completeSearchLoading`이 1,500ms 동안 진행 카드를 유지한다. 결과가 적거나 0건이어도 사용자가 기다려야 한다. 실제 작업과 무관한 카운트 애니메이션을 줄이고 결과를 바로 보여주는 것이 좋다. `data_managing_page.dart` 근거의 개선 제안이며 실기 성능 벤치마크 수치가 아니다.
- 고정지출 복사·태그 창은 새 카드형 팝업인데 여행 삭제·튜토리얼 종료·CSV 성공·가져오기 성공은 별도의 `AlertDialog`를 사용한다. 버튼 위치도 공통 카드형은 왼쪽, 기본 팝업은 오른쪽으로 달라진다. [고정지출 복사](beta_test_evidence/android_fixed_carryover_offer.png), [여행 삭제](beta_test_evidence/android_trip_delete_warning.png), [튜토리얼 종료](beta_test_evidence/android_tutorial_exit.png), [가져오기 완료](beta_test_evidence/android_import_success.png). 경고/완료의 색상 차이는 유지하되 여백·본문 폭·버튼 정렬을 통일할 필요가 있다.
- PDF는 단 2개 일반 지출로 5쪽이 만들어졌으며, 추세 차트의 제목과 그림이 페이지 경계에서 나뉘고 후속 페이지에 넓은 빈 공간이 생겼다. 핵심 요약과 상세 부록의 페이지 구분은 유지하면서 제목·그림 묶음과 작은 표의 배치를 조정하면 좋다.

### B16. PDF 재생성 시 이전 파일을 조용히 교체

같은 프로필 Beta·2026년 9월로 PDF를 두 번 생성했다. 두 결과 모두 `Household_ledger_report_Beta_2026-09.pdf`로 저장되며, 기존 보고서 목록에는 새 생성 시각의 파일 하나만 남았다. 덮어쓰기 확인은 없었다. 기존 파일을 보관하려던 사용자는 이전 보고서를 잃을 수 있다.

`export_pdf_report_service.dart:381`에서 이름·기간만으로 파일명을 만들고 `writeAsBytes`로 덮어쓴다. 생성 시각을 파일명에 추가하거나 교체 여부를 묻는 것이 좋다. ## 화면 크기별 검사 범위

Android의 density는 모두 320이며 아래 크기는 논리 화면 크기다. 상태바·내비게이션·키보드가 차지하는 공간은 별도다.

| 조건 | 글자 배율 | Android 확인 화면 | 주요 결과 |
|---|---:|---|---|
| 320×568dp, 한국어 | 1.0 | 홈·소비기록·고정지출·수입·분석 | 소비기록 하단 넘침 |
| 393×852dp, 한국어 | 1.0 | 위 5개 화면 및 대부분의 기능 조작 | 달력을 펼치면 기록 목록 공간이 매우 좁음 |
| 640×360dp, 한국어 | 1.0 | 위 5개 화면, 태그 팝업+키보드 | 소비기록 및 팝업 넘침 |
| 800×1280dp, 한국어 | 1.0 | 위 5개 화면 | 해당 핵심 화면에서 넘침 경고 미관찰; 넓은 여백의 활용 개선 여지 |
| 360×640dp, 한국어 | 1.8 | 홈·소비기록·고정지출·수입 | 소비기록 348px 넘침; 분석 캡처 도중 에뮬레이터 종료 |
| 320×568dp, 일본어 | 1.3 | 홈·소비기록·분석 | 소비기록과 분석 기간 선택부 넘침 |
| 360×640dp, 일본어 | 1.8 | 분석, 지출 0건 | 기간 선택부 40px 넘침 |

핵심 화면 캡처는 기본 행렬 24개 + 일본어 4개다. 모든 화면을 모든 해상도에서 수동 조작했다는 의미는 아니다. [기본 Android 행렬](beta_test_evidence/android_matrix.json)에 개별 파일과 크기를 기록했다.

별도 Widget 검사는 16개 라우트 × 6조건 = **96개**다. 진단이 나온 조합은 19개이며 실제 레이아웃 넘침은 7개 조합이다. 나머지 12개는 설정·PDF 페이지의 ListTile/ink 관련 진단이다. Widget 검사에서는 가로 초기 설정 화면의 70px 넘침도 수집했으나 Android에서 같은 조건을 재현하지 않아 확정 결함 수에 더하지 않았다. [전체 결과](beta_test_evidence/screen_matrix.json).

이 검사 스크립트는 Flutter 오류를 수집하고 다음 화면으로 진행한다. 따라서 실행 로그의 96개 통과는 **검사 완료**를 뜻하며 UI가 모두 정상이라는 의미가 아니다. 호스트 글꼴·플러그인 대체 및 앱 루트 배경 차이도 있어 색상·네이티브 기능 판정에는 Android 증거를 우선했다.

## 수정 우선순위와 재검증 기준

1. **데이터 보존:** B02·B03을 먼저 수정한다. 손상/중복 백업은 현재 DB를 변경하기 전에 거절하고, 정상·구버전 복원의 종류별 건수와 합계를 검증한다.
2. **핵심 입력 접근:** B01·B09를 수정한다. 320×568dp 및 640×360dp 키보드 표시 상태에서 목록·입력·확인 버튼에 스크롤로 도달할 수 있어야 한다. 이어 B04의 확대 글자 조건을 확인한다.
3. **생성 파일 신뢰성:** B10·B11·B16을 수정한다. 신규 설치·비행기 모드에서 한·일 PDF 글꼴이 표시되고, 도넛과 범례가 같은 분모를 쓰며, 이전 파일 보존 여부를 알 수 있어야 한다.
4. **사용성 정리:** 상태바 대비·접근성 이름·요일 현지화·암호 입력 안내·백업 보관·팝업 통일·검색 지연을 정리한다.

## 아직 완료 판정하지 않은 범위

실물 Android 기기/OEM별 차이, 장기간 사용·실제 월 경계 경과, 앱 종료 상태의 예약 알림 수신, 저사양 기기 성능·배터리는 별도 검증이 필요하다. 에뮬레이터 초기 System UI 응답 지연, ARM용 APK를 x86_64에 올렸을 때의 ABI 오류, 해상도 변경 중 에뮬레이터 프로세스 종료는 검사 환경 문제로 분리했다.

후반 재실행은 호스트 GPU와 Impeller 비활성 옵션을 사용했다. 모든 결과가 동일 렌더러 설정에서 나온 것은 아니다. 대량 데이터 성능, 가져오기 도중 강제 종료·저장소 부족·부분 실패, 구형 설치 DB migration의 Android 실기 검증, TalkBack 직접 청취도 남아 있다. 따라서 이 보고서는 전 기능·전 기기의 출시 승인서가 아니라, 확보된 재현 결과와 남은 검증 범위를 정리한 베타테스트 결과다.
