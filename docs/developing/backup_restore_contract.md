# 백업 검증·복구 계약

이 문서는 [후속 지침서](beta_remediation_and_multidevice_ui_guide.md)의 순서 1(B02·B03)에 해당하는 변경을 설명한다. CSV 출력은 3.0을 유지하며 DB schema 변경은 없다.

## 검증

- 모든 지원 버전: 명시적인 버전을 요구하며, 버전 누락을 임의로 v1로 간주하지 않는다. 중복 섹션·잘못된 인용·행 길이·중복 설정·존재하지 않는 날짜·중복 데이터 ID를 거절한다. 수입의 비어 있지 않은 ID는 정수여야 하며 중복을 허용하지 않는다.
- v1/v2: 여행 섹션이 없어도 복원한다. 지출 헤더는 필요하며 구형 파일에 없는 보조 섹션은 허용한다. 여행 연결은 비운다. 정상적인 구형 데이터는 유지하지만 잘못된 행을 조용히 건너뛰는 동작은 더 이상 허용하지 않는다.
- v3: 지출·고정지출·수입·여행·설정·태그 섹션과 필수 헤더를 요구한다. 지출에는 tripId 열, 설정에는 localeCode/currencyUnit/monthlyBudget을 요구한다. iconCode는 아이콘 도입 전 백업을 위해 선택적이다.
- 태그는 종류+코드가 유일해야 한다. 참조 코드는 백업에 있거나 시스템 기본 코드여야 한다. 누락된 구형 식사 유형에는 기존 기본값 복원을 유지한다.
- 정상적인 헤더+0행은 빈 목록이다. 파일 검증 후 종류별 건수와 전체 교체 범위를 보여주며, 확인한 동일 파싱 결과를 저장한다. 취소 시 저장소 변경은 없다.

현재 형식에는 섹션별 건수·본문 checksum이 없다. 구조가 유지된 채 완전한 데이터 행만 삭제되면 이를 탐지할 수 없다. 이를 보완하는 새 형식은 별도 버전으로 도입해야 한다. 기존 signature는 이메일/문자열 키의 일치 확인이며 본문 암호화나 작성자 인증이 아니다.

## 복구 경계

`BackupRestoreService`는 지출·고정지출·수입·여행과 다음 설정 키를 함께 교체한다: `household_ledger_state`, 활성 여행 키, `tutorial_completed`, `tutorial_version`. 이전 키가 없었다면 복구 시에도 키를 제거해 부재를 보존한다. ID 없는 구형 수입에는 충돌하지 않는 ID를 부여한다.

1. 입력 ID·여행 참조 검증 및 진행 중 작업 차단.
2. 미완료 복구본이 있다면 먼저 이전 상태 복구.
3. 현재 전체 DB와 해당 설정의 원문을 복구본에 저장하고 다시 읽어 확인.
4. 각 저장소를 교체하고 전체 레코드·설정을 다시 읽어 비교. 순서 차이는 허용하되 건수·금액·참조·본문 차이는 허용하지 않음.
5. 기존 식사 설명 migration과 현재 월 Provider 상태 구성을 완료한 뒤 복구본 삭제.
6. 복구본 삭제 후 메모리 상태 공개. 실패 시 원본을 복원하고, 복원도 실패하면 복구본을 유지하고 정상 쓰기 상태를 노출하지 않음.

네이티브 복구본은 앱 지원 디렉터리의 `pending_ledger_import_v1.json`이다. 임시 파일을 flush한 뒤 이름을 바꿔 공개한다. 완료 표시는 복구본 삭제이며, 그 전에 프로세스가 종료되면 다음 시작에서 이전 상태로 되돌린다. Web 대체 저장은 동일 이름의 SharedPreferences 키를 쓴다. 별도 DB들의 교체 전체를 하나의 SQLite transaction이라고 표현하지 않는다.

`main()`은 Provider·여행 초기화 전에 복구를 실행한다. 실패 시 복구 재시도 화면을 표시한다. 복구 파일 손상·계속되는 저장소 오류를 자동으로 무시하거나 복구본을 지우지 않는다. 정상 import 중 앱 생명주기의 기존 상태 저장은 건너뛰어 가져온 설정을 덮어쓰지 않는다.

파일 flush/rename은 일반적인 앱 프로세스 종료 복구를 위한 처리이며 물리 저장 장치 고장까지 보장하는 외부 백업은 아니다. 실제 사용자 금액·메모·백업 본문을 새 로그에 추가하지 않는다.
